================================================================================
1. BUSINESS MODEL — WHAT THIS SYSTEM DOES
================================================================================

Yumas is a restaurant group with four locations:

  Westend     restaurant
  Eschborn    restaurant
  Taunus      restaurant
  ZK          production kitchen ("Zentralküche") — supplies the other three

The central kitchen (ZK) produces prepared goods (salsas, marinades, proteins,
tortillas) and delivers them to the three restaurants on a fixed weekly cycle.

The core loop the software automates:

  1. Before a delivery, each restaurant COUNTS its current stock
     ("inventory submission").
  2. The system compares that count to a TARGET stock level for that store and
     that weekday.
  3. The difference becomes the DELIVERY QUANTITY — how much ZK must send.
  4. ZK PACKS the delivery, recording what was actually packed (which may
     differ from what was requested).
  5. A DRIVER delivers it; each store CONFIRMS receipt.
  6. The next inventory count closes the cycle, allowing CONSUMPTION to be
     derived: what was actually used between two deliveries.

Deliveries run on four weekdays only: MONDAY, TUESDAY, WEDNESDAY, FRIDAY.
This is hard-coded in several places as `[1, 2, 3, 5]` (JS day-of-week) and as
the column set `mon/tue/wed/fri`. There is no Thursday, Saturday or Sunday
delivery. Any reimplementation must decide early whether to keep this
four-day assumption or generalise it — it is baked in deeply.

All tables are PostgreSQL via Supabase. Row Level Security is enabled on all of
them, but the policies are uniformly permissive:

    FOR ALL TO authenticated USING (true) WITH CHECK (true)

i.e. any signed-in user can read and write everything. Access control is
enforced in the UI layer only (see Section 6.2). This is a significant design
weakness to reconsider when rebuilding.

3.1 INVENTORY LISTS            /inventory/lists          (managerOnly)
--------------------------------------------------------------------------------
File: app/(app)/inventory/lists/page.tsx  (~1,126 lines)

The master-data editor. Everything downstream depends on what is configured

Responsibilities:
  - CRUD on inventory_items: name, unit, section, which stores carry it.
  - CRUD on inventory_sections: name, which stores, sort order.

  - Per-store, per-weekday TARGET quantities (store_targets), i.e. the four

  - Bulk clear of a store's targets via RPC `clear_store_targets(p_store)`.

Concurrency:
  On mount the page calls `acquire_edit_lock` with a page key; on unmount it
  calls `release_edit_lock`. If another user holds the lock, the UI shows who
  and blocks editing. Lock expires after 5 minutes.

Sorting rule used consistently across the app:
  section order  = inventory_sections.sort_order (filtered to this store)
  item order     = store_sort_orders[store]  ??  sort_order

3.2 ADD NEW INVENTORY          /inventory/add            (perm `inventory`)
--------------------------------------------------------------------------------
Files:
  app/(app)/inventory/add/page.tsx               (~180 lines)  location picker
  app/(app)/inventory/add/[locationId]/page.tsx  (~1,007 lines) the count form

This is the highest-traffic screen — staff use it on a phone, standing in a
cold room. It is the most engineered page in the two sections.

Behaviour:
  - Loads inventory_items filtered to this store, grouped into sections,
    ordered by the per-store rule above.
  - Renders one numeric input per item. Sections are collapsible.
  - A STOPWATCH runs from first interaction; the elapsed time is saved as
    duration_seconds so managers can see how long counts take.
  - AUTO-SAVE DRAFT: every ~800 ms after the last keystroke the partial count
    is written to localStorage (lib/draft-store.ts) keyed by locationId. On
    remount the draft is restored. Prevents loss if the phone locks.
  - OFFLINE QUEUE: if the device is offline at submit time the submission is
    written to IndexedDB (lib/offline-queue.ts, database 'yumas-offline' via
    the `idb` package). An online/offline event listener drains the queue
    automatically when connectivity returns. A badge shows the pending count.
  - EDIT WINDOW: a submission can be edited by its author until 09:00 the
    following day. Implemented as:

        function isEditable(submittedAt) {
          const deadline = new Date(submittedAt);
          deadline.setDate(deadline.getDate() + 1);
          deadline.setHours(9, 0, 0, 0);
          return new Date() < deadline;
        }

    On the first edit the original payload is copied into `original_data` so
    the initial count is never lost. Subsequent edits overwrite `data` only.
  - Managers can reorder items and move an item between sections directly from
    this screen (mutations write back to inventory_items).
  - The most recent submission for the location can be loaded to pre-fill the
    form (useful when little has changed).

The `data` written is an array:  [{ name, quantity }, ...]
using the item NAME as identifier, not the id.

3.5 USAGE FORECAST             /inventory/usage-forecast (managerOnly)
--------------------------------------------------------------------------------
File: app/(app)/inventory/usage-forecast/page.tsx  (~613 lines)

Predicts how much of each item a shift will consume.

Model: each item has a baseline usage per store and per shift type stored in
usage_standards (lunch_c, dinner_c — the "C" level meaning normal trade). A
five-band multiplier scales that baseline for busier or quieter shifts:

    const MULTIPLIERS = { A: 0.5, B: 0.75, C: 1, D: 1.25, E: 1.5 };
    compute(c, key) = round(c * MULTIPLIERS[key] * 10) / 10

So a shift graded "D" is expected to use 1.25x the normal quantity. The UI
displays a matrix of items x A..E bands per store.

Also includes an upload modal to bulk-set usage_standards per store.

--------------------------------------------------------------------------------
4.1 STAGES                     /delivery                 (the main workflow)
--------------------------------------------------------------------------------
File: app/(app)/delivery/page.tsx  (~2,651 lines — by far the largest file)

ONE page, FOUR view modes:

    type ViewMode = 'manager' | 'packer' | 'driver' | 'store';

Mode is chosen by, in order:
  1. `?view=` query parameter, if one of the four
  2. localStorage 'delivery-view-mode'
  3. the user's permissions: driver -> 'driver', packer -> 'packer'
  4. default 'packer'

Staff-only sidebar shortcuts exist:
    /delivery?view=packer   (permission `packer`)
    /delivery?view=driver   (permission `driver`)

THE WORKFLOW, in stages:

  STAGE 1 — LIST CONFIRMATION (manager)
    A delivery run is created (or previewed) for the target date. The manager
    reviews each store's computed quantities, may override target_qty per line,
    and confirms each store's list. Confirmation writes
    list_confirmed_<store>_at. When all three are confirmed the day can be
    locked (day_locked_at / day_locked_by), freezing the list.

  STAGE 2 — PACKING (packer, at ZK)
    packing_started_at is set. The packer walks each store's list and records
    packed_qty per line. packed_qty is deliberately separate from delivery_qty
    so shortfalls are visible: a line can be requested 10 and packed 7.
    The UI classifies lines as fully packed (packed_qty >= delivery_qty),
    partially packed (0 < packed_qty < delivery_qty) or unpacked (NULL).
    Per-store completion timestamps go into store_packing_finished_at (jsonb).
    On completion: packing_finished_at, packing_duration_seconds,
    items_packed_count, packed_by.
    The packer view polls every 15 seconds (refetchInterval: 15_000).

  STAGE 3 — DELIVERY (driver)
    delivery_started_at / delivery_started_by set on departure. A
    delivery_snapshot (jsonb) freezes the line state at dispatch so later edits
    cannot rewrite history. On completion delivery_finished_at /
    delivery_finished_by. The driver view also polls every 15 seconds.

  STAGE 4 — STORE RECEIPT (store staff, permission `store_receiver`)
    Each store confirms arrival, ticking off items. Writes
    store_delivery_receipts with confirmed_item_ids, items_confirmed_count,
    received_by, received_at and free-text notes.

Stores served: Westend, Eschborn, Taunus. ZK is excluded from the packing view
(`STORES.filter(s => viewMode !== 'packer' || s !== 'ZK')`) because ZK is the
source, not a destination.

A "skipped_stores" array on the run allows a store to be omitted from a
delivery day.

    Tuesday Lunch only, because there is no Monday Dinner shift to bridge. The
    Friday cycle ends at Saturday Dinner.

For a rebuild this is documentation, not functionality — but the rules it
encodes are real operational constraints that the target quantities assume.

5. CORE ALGORITHMS
================================================================================

--------------------------------------------------------------------------------
5.1 BUILDING A DELIVERY RUN
--------------------------------------------------------------------------------
Source: app/(app)/delivery/page.tsx (~line 1890)

Given a target delivery date:

  dayKey = one of 'mon' | 'tue' | 'wed' | 'fri' derived from the date

  1. Upsert delivery_runs on delivery_date (unique), status 'draft'.
  2. DELETE all existing delivery_run_lines for that run  (full rebuild, not
     incremental — any manual edits are lost on regeneration).
  3. For each store (Westend, Eschborn, Taunus):
       a. Load inventory_items where stores @> [store].
       b. Load the latest inventory_submission for that store linked to this
          delivery date.
       c. For each item:

            effectiveTarget = max(0, store_targets[store][dayKey] ?? 0)

            reportedQty = quantity from the submission where
                          item.name.trim().toLowerCase()
                          === submitted.name.trim().toLowerCase()
                          else 0

            deliveryQty = max(0, effectiveTarget - reportedQty)

       d. Insert a delivery_run_line with
            standard_target_qty = effectiveTarget
            target_qty          = effectiveTarget
            reported_qty        = reportedQty
            delivery_qty        = deliveryQty
            packed_qty          = NULL
            is_packed           = false

  4. If every store has a submission, the run is considered fully sourced.
  5. Copy the submissions' comments into delivery_runs.store_inventory_comments.

PREVIEW MODE: if no run exists yet for the date, the same shape is built in
memory from store_targets with reported_qty = 0 and delivery_qty = target, so
managers can see a provisional list before any store has counted. Only items
with a target > 0 for that weekday appear.

--------------------------------------------------------------------------------
5.2 DEMAND SCALING
--------------------------------------------------------------------------------

Targets are calibrated to a "standard" trading day. When a manager forecasts
sales above or below that standard, targets scale proportionally:

    standard = store_day_standards.standard_sales_eur
               for (store, dayKey)

    forecast = weekly_sales_forecasts.forecasted_sales_eur
               for (store, delivery_date)

    scale    = standard > 0 ? forecast / standard : 1

    if no forecast exists  ->  scale = 1.0 (targets used as-is)

The UI surfaces this as a banner: "Forecast for Westend: 3.000 € x1.20 (120%)",
highlighting when the scale is more than 2% away from 1.0.

In the current live code the scale is applied in the manager UI layer when
proposing target_qty; the persisted `standard_target_qty` always holds the
unscaled figure so the original is recoverable.

The abandoned delivery_targets table had a per-row `scales_with_demand` boolean
and a `demand_scale_factor` so that, e.g., cleaning chemicals would not scale
with sales while food would. That granularity is NOT present in the live
store_targets design. If you need it, reintroduce it deliberately.

--------------------------------------------------------------------------------
5.3 CONSUMPTION PER DELIVERY CYCLE   *** the most valuable algorithm ***
--------------------------------------------------------------------------------
Source: app/api/inventory/movements/[store]/route.ts

For a given store, reconstructs what was actually consumed between deliveries.

  1. Load all delivery_runs ordered by delivery_date ascending.
  2. Keep only runs that have delivery_run_lines for this store.
  3. Group those lines by run.
  4. Load inventory_submissions for this store where
       linked_delivery_date IN (all relevant delivery dates + the NEXT run's
       date after the last relevant one)
     and deleted_at IS NULL, newest first. Keep only the LATEST submission per
     linked_delivery_date.
  5. Build the canonical item list: inventory_items filtered to this store,
     sorted by inventory_sections.sort_order then
     store_sort_orders[store] ?? sort_order.
  6. For each run i:

       preInv   = the submission linked to run[i].delivery_date
                  -> map of item name -> quantity
       delivery = for each line of run[i]:  packed_qty ?? delivery_qty ?? 0
                  (only where > 0)
       postInv  = the submission linked to run[i+1].delivery_date

       if postInv exists, for every item in the master list:

           consumption[item] = preInv[item] + delivery[item] - postInv[item]

       (missing values default to 0)

  7. Return { store, items[], cycles[] } where each cycle carries
     deliveryDate, preInvDate, postInvDate, preInv, delivery, postInv,
     consumption.

Note the fallback `packed_qty ?? delivery_qty`: if the packer recorded what was
actually packed, that is used; otherwise the requested quantity is assumed.
This matters — using requested rather than packed quantities silently
overstates consumption whenever a delivery was short.

--------------------------------------------------------------------------------
5.4 ORDERING RULE (used everywhere — get this right once)
--------------------------------------------------------------------------------

    sections: inventory_sections filtered by stores @> [store],
              ordered by sort_order ascending
    items:    inventory_items filtered by stores @> [store],
              ordered by (section's sort_order,
                          store_sort_orders[store] ?? sort_order)

This ordering is deliberately the physical walking order of each store's
storage areas. Getting it wrong makes counting slower and error-prone, which is
the whole reason it is per-store.

--------------------------------------------------------------------------------
5.5 DAY BOUNDARY RULE
--------------------------------------------------------------------------------

    EOD_CUTOFF_HOUR = 4

A timestamp between 00:00 and 03:59 belongs to the PREVIOUS calendar day.
Applied when grouping submissions by day in Current Inventory. Late-shift
counts routinely happen after midnight.

================================================================================
7. KNOWN DEFECTS AND TRAPS
================================================================================

Do not reproduce these. They were found by auditing the live system.

7.1  delivery_targets DOES NOT EXIST
     supabase/delivery_system.sql creates it; the live database has no such
     table; /delivery/targets queries it and therefore throws. Targets live in
     inventory_items.store_targets. The page is unreachable from the sidebar,
     which is why nobody has noticed.

7.2  NAME COLLISION: "delivery reports"
     The table `delivery_reports` holds delivery-PLATFORM sales (Wolt/Lieferando
     style: orders_count, net_revenue, shift_type). The PAGE "Delivery Reports"
     (/delivery/reports) is about ZK delivery RUNS and does not read that table.
     Two unrelated concepts, one name. Rename on rebuild.

7.3  ITEMS ARE JOINED BY NAME, NOT ID
     inventory_submissions.data stores { name, quantity }. Delivery run
     construction matches on
        item.name.trim().toLowerCase() === submitted.name.trim().toLowerCase()
     Renaming an item in inventory_items silently breaks the match against all
     historic submissions, and the item then reads as zero stock — which
     inflates the next delivery quantity. USE IDs.

7.4  POSTGREST 1000-ROW CAP
     Supabase/PostgREST silently truncates any unpaginated query at 1000 rows
     with no error. delivery_run_lines already holds 17,183 rows. Several
     queries elsewhere in this codebase were found to be silently truncated for
     months. ALWAYS paginate with .range(), or use an explicit count and loop.
     A helper exists at lib/fetch-all.ts.

7.5  FULL REBUILD ON REGENERATE
     Regenerating a delivery run DELETEs all its delivery_run_lines and
     reinserts. Any manual target_qty edits or packed_qty values are lost.
     There is no warning in the UI.

7.6  RLS IS EFFECTIVELY OFF
     Every policy is USING (true) WITH CHECK (true) for authenticated users.
     All access control is client-side. Any authenticated user could read or
     write any store's data via the API directly.

7.7  STORE LIST HARD-CODED IN MULTIPLE PLACES
     `const STORES = ['Westend', 'Eschborn', 'Taunus'] as const;` appears in
     several files, sometimes with ZK, sometimes without. Adding a fourth
     restaurant means editing many files. Drive this from the locations table.

7.8  DELIVERY WEEKDAYS HARD-CODED
     `[1, 2, 3, 5]` and the mon/tue/wed/fri key set appear in the schema, the
     targets JSON shape, and several pages. Changing the delivery schedule is a
     migration, not a setting.

7.9  SECTION sort_order IS NOT GLOBALLY UNIQUE
     Values repeat across stores (two sections share 10, two share 20, ...).
     It is only meaningful within a store's filtered set. Sorting without
     filtering by store first gives nondeterministic order.

7.10 UNUSED TABLES
     inventory_levels, delivery_schedules, daily_forecasts are all empty and
     unwritten. shift_usage has 1 row. Do not port them without deciding
     whether the feature is actually wanted.

8.2  DESIGN CHANGES WORTH MAKING

     - Reference inventory_items by ID in submissions and run lines, keeping
       name/unit only as a display snapshot.

     - Enforce permissions in RLS, not React.

       a data layer.
     - Make the delivery weekday set and the store list configuration, not
       constants.
     - Represent the run workflow as an explicit state machine rather than a
       dozen nullable timestamps.
     - Decide up front whether targets scale with forecast per item (the
       abandoned scales_with_demand idea) — retrofitting it is painful.

     app/(app)/inventory/  ~5,800 lines across 9 files

8.4  THE THINGS THAT ARE EASY TO UNDERESTIMATE

     - The offline path in the count form (IndexedDB queue + draft autosave +
       online/offline listeners + reconciliation). It exists because staff
       count stock in cold rooms with no signal.
     - The per-store item ordering. It looks cosmetic; it is the difference
       between a 12-minute and a 25-minute stock count.
     - The 04:00 day-boundary rule and the 09:00-next-day edit window. Both are
       invisible until they are wrong.
     - packed_qty vs delivery_qty. Keeping them distinct is what makes
       consumption analysis honest.
